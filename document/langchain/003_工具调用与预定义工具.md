# 003：工具调用与预定义工具

> 本篇对应当前项目中的 `app/tool.py`、`app/chain.py` 和 `app/config.py`。
>
> 学习目标：理解模型为什么不能自己访问外部世界、工具调用的消息循环如何工作，以及如何把自定义工具和官方预定义工具挂到现有 LCEL 链上。

---

## 一、我们要解决什么问题？

​	但模型本身仍然只是一个“根据上下文生成下一句话”的程序。

如果用户问：

```text
我现在在哪里？
用 Tavily 搜索 LangChain 是什么，并写入 intro.txt
```

​	只把问题发给模型是不够的。模型可能会编造一个地点，或者假装已经写好了文件。要让回答落到真实世界，需要给它一组**可执行的工具**。

本项目把工具定义和调用循环放在：

```text
app/tool.py     定义工具、组装工具列表、执行工具循环
app/chain.py    把工具绑定到模型，并接入现有问答链
app/config.py   读取 TAVILY_API_KEY
outputs/        write_txt_file 默认写入的目录
```

---

## 二、模型不会自己执行工具

这是最容易误解的一点。

工具调用不是“模型直接运行 Python 函数”，而是一次**分工**：

```text
用户提问
   ↓
把工具的名字、参数说明发给模型
   ↓
模型决定：要不要调用工具？调用哪一个？参数是什么？
   ↓
我们的代码真正执行函数
   ↓
把执行结果作为 ToolMessage 送回模型
   ↓
模型根据工具结果生成最终自然语言回答
```

模型负责“决策”，程序负责“执行”。

因此，一条带工具的对话通常不是一轮请求，而是多轮模型调用：

```text
第 1 次模型调用：返回 tool_calls
执行 get_current_location()
第 2 次模型调用：看到工具结果，回答“你当前在 Beijing”
```

`002` 里已经介绍过 `AIMessage.tool_calls` 和 `ToolMessage`。本篇把它们接到真实代码上。

## 三、什么是预定义工具？

LangChain 里的工具，本质是一份给模型看的说明书，外加一份给我们执行的函数。常见来源有两类：

| 类型 | 怎么得到 | 本项目例子 |
|---|---|---|
| 自定义工具 | 用 `@tool` 把普通函数包装成工具 | `get_current_location`、`write_txt_file` |
| 官方/集成工具 | 安装对应包后直接实例化 | `langchain_tavily.TavilySearch` |

自定义工具适合教学和业务逻辑：位置查询、写文件、查数据库、调内部 API。

官方工具适合已经有稳定协议的外部服务：网页搜索、网页抓取、地图、代码解释器等。它们通常已经写好了参数 schema、错误处理和返回格式，不必从零封装 HTTP 请求。

无论来源是哪一种，对模型来说长相差不多：都有 `name`、`description` 和参数结构。

## 四、用 `@tool` 定义自定义工具

LangChain 的 `@tool` 会读取函数名、类型注解和 docstring，自动生成工具 schema。

```python
from langchain_core.tools import tool

@tool
def get_current_location() -> str:
    """查询当前所在的地理位置。不需要传入参数。"""
    return "Beijing"
```

装饰之后，`get_current_location` 不再只是普通函数，而是一个 `BaseTool`：

```python
get_current_location.name        # "get_current_location"
get_current_location.description # 来自 docstring
get_current_location.invoke({})  # 真正执行，返回 "Beijing"
```

教学上这个工具故意**不实现定位**，直接返回 `"Beijing"`。重点不是 GPS，而是走通“模型请求工具 → 代码执行 → 结果回填”这条路径。

写文件工具带参数：

```python
@tool
def write_txt_file(filename: str, content: str) -> str:
    """把文本内容写入本地 txt 文件。

    当用户要求保存、记录或导出文字时使用本工具。

    Args:
        filename: 文件名，必须是 .txt 结尾，例如 notes.txt。不要包含目录。
        content: 要写入文件的完整文本内容。
    """
    ...
```

模型看到的大致是：

```text
工具名：write_txt_file
功能：把文本写入本地 txt 文件
参数：
  filename: string
  content: string
```

docstring 很重要。模型主要靠这段文字判断“什么时候该用这个工具”。写得含糊，模型就会乱用或不用。

可以直接在 Python 里试用，不必经过模型：

```python
from app.tool import get_current_location, write_txt_file

print(get_current_location.invoke({}))
print(write_txt_file.invoke({"filename": "hello.txt", "content": "你好"}))
```

## 五、本项目的三个预定义工具

`get_tools()` 负责组装当前可用工具：

```python
tools = [get_current_location, write_txt_file]
# 配置了 TAVILY_API_KEY 时再追加 TavilySearch
```

### 1. `get_current_location`：最简单的示范工具

- 无参数。
- 固定返回 `"Beijing"`。
- 用来验证工具调用链路是否通。

适合问：

```text
我现在在哪里？
查询当前地理位置
```

### 2. `write_txt_file`：让模型能写 txt

默认写入项目根目录下的 `outputs/`。它做了几件安全相关的事：

1. 只用文件名，丢掉路径中的目录部分。
2. 只允许 `.txt`。
3. 用 `resolve()` + `relative_to()` 防止写到输出目录之外。
4. 使用 UTF-8 编码。

因此即使用户或模型传入 `../secret.txt`，实际仍会写到 `outputs/secret.txt`，而不是项目外面。

成功后返回类似：

```text
已将内容写入：D:\code\Langchain\outputs\intro.txt
```

模型再根据这句话告诉用户“文件已经写好”。

### 3. `tavily_search`：官方库工具

这是 Tavily 提供给 LangChain 的现成搜索工具，不是我们手写的 HTTP 客户端：

```python
from langchain_tavily import TavilySearch

TavilySearch(
    max_results=5,
    topic="general",
    tavily_api_key=api_key,
)
```

它的工具名是 `tavily_search`。调用时模型通常会传入：

```python
{"query": "LangChain 是什么"}
```

返回的是搜索结果 JSON：标题、链接、摘要等。`run_tool_loop` 会把它序列化成文本，再作为 `ToolMessage` 交给模型总结。

## 六、如何把工具交给模型：`bind_tools`

只定义工具还不够。必须告诉模型“你现在可以使用这些工具”。

`app/chain.py` 中的关键一句是：

```python
llm = model.bind_tools(tools) if tools and hasattr(model, "bind_tools") else model
```

`bind_tools` 不会执行工具，它只是把工具 schema 附加到之后的模型请求上。底层请求里会多出类似这样的信息：

```json
{
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "get_current_location",
        "description": "查询当前所在的地理位置。不需要传入参数。",
        "parameters": {"type": "object", "properties": {}}
      }
    }
  ]
}
```

支持工具调用的模型看到后，可能返回普通文本，也可能返回结构化的 `tool_calls`：

```python
AIMessage(
    content="",
    tool_calls=[
        {
            "name": "get_current_location",
            "args": {},
            "id": "call_loc_1",
            "type": "tool_call",
        }
    ],
)
```

## 七、工具循环：从 `tool_calls` 到 `ToolMessage`

执行逻辑在 `app/tool.py` 的 `run_tool_loop()`。可以把它看成一个有上限的 while 循环：

```text
调用模型
  如果没有 tool_calls → 把回复当最终答案返回
  如果有 tool_calls   → 逐个执行工具
                      → 追加 ToolMessage
                      → 再次调用模型
最多 8 轮，防止模型反复调工具停不下来
```

对应代码结构：

```python
response = llm.invoke(messages, config=config)
tool_calls = getattr(response, "tool_calls", None) or []
if isinstance(response, str) or not tool_calls:
    return _message_text(response)

messages.append(response)
for tool_call in tool_calls:
    result_text = selected.invoke(args)
    messages.append(ToolMessage(content=result_text, tool_call_id=call_id))
```

以“我现在在哪里？”为例，循环内部的消息大致是：

```python
[
    SystemMessage(...),
    HumanMessage(content="我现在在哪里？"),
    AIMessage(content="", tool_calls=[{"name": "get_current_location", ...}]),
    ToolMessage(content="Beijing", tool_call_id="call_loc_1"),
]
```

第二次调用模型时，它已经看到工具返回了 `Beijing`，于是生成：

```text
你当前在 Beijing。
```

模型调用工具的一轮对话可以看成是一个循环，结构类似:

![image-20260915122329481](https://cdn.jsdelivr.net/gh/APpery1/pic@main/img/image-20260915122329481.png)

注意两点：

1. `ToolMessage` 必须带 `tool_call_id`，用来对应刚才那一次工具请求。不要把工具结果伪装成 `HumanMessage`。
2. 工具报错时，本项目把错误字符串返回给模型，而不是直接让整个程序崩溃。模型还可以向用户解释“搜索失败，因为没有配置 Key”。

`002` 里强调过：做工具调用时，优先使用 `AIMessage` / `ToolMessage` 对象，而不是手写 `{"role": "..."}` 字典。原因就是 `tool_calls` 和 `tool_call_id` 用对象表达更清楚。

## 八、它是如何接到现有链上的？

第一篇的链是：

```python
prompt | model | StrOutputParser()
```

加上工具后变成：

```python
prompt | RunnableLambda(call_model) | output_parser
```

`call_model` 做的事情是：把 Prompt 展开成消息列表，再交给 `run_tool_loop`。

```python
def call_model(prompt_value, config=None):
    messages = list(prompt_value.to_messages())
    return run_tool_loop(llm, messages, tools, config=config)
```

完整数据流：

```text
{"question": "我现在在哪里？"}
   ↓
ChatPromptTemplate 生成系统消息 + 历史 + 当前用户消息
   ↓
run_tool_loop
   ↓
bind_tools 后的 ChatOpenAI
   ↓
可能多次：模型 ↔ 工具
   ↓
得到最终字符串
   ↓
StrOutputParser
   ↓
CLI 打印
```

系统提示词会根据实际工具变化：

```python
if tools:
    tool_names = "、".join(item.name for item in tools)
    system_prompt += f" 需要时可以调用这些工具：{tool_names}。"
```

没有 Tavily Key 时，模型只会看到：

```text
需要时可以调用这些工具：get_current_location、write_txt_file。
```

有 Key 时才会多出 `tavily_search`。

CLI 仍然是：

```python
chain.invoke({"question": question}, config=config)
```

`app/main.py` 不需要知道工具的存在。工具对调用方是透明的。

## 九、工具消息会不会进入会话历史？

当前项目的历史机制仍是 `RunnableWithMessageHistory`。它按“当前问题 + 最终答案”记账：

```text
HumanMessage：我现在在哪里？
AIMessage：你当前在 Beijing。
```

也就是说：

- **这一轮内部**的 `tool_calls` 和 `ToolMessage` 发生在 `run_tool_loop` 里，用于完成本次回答。
- **跨轮历史**默认只保留用户问题和最终回复，不会把每一次工具调用都存进 `InMemoryChatMessageHistory`。

这样更简单，也和现有测试一致。如果以后要让模型在下一轮继续看到“刚才搜过什么”，就需要把完整消息，包括 `ToolMessage`，一并写入历史，或改用 LangGraph 的持久化。学习阶段先分清这两层即可。

## 十、运行示例

确保已安装依赖，其中包含与本项目 LangChain 0.3 匹配的官方 Tavily 集成：

```bash
pip install -e .
```

`pyproject.toml` 中对应的是：

```text
langchain-tavily>=0.2.11,<0.2.12
```

只测本地工具，不需要 Tavily Key：

```bash
python -m app.main "我现在在哪里？"
python -m app.main "把一句话介绍 LangChain 写入 intro.txt"
```

第二个例子成功后，查看：

```text
outputs/intro.txt
```

要启用网页搜索，先配置 `.env`：

```env
TAVILY_API_KEY=你的_tavily_key
```

然后：

```bash
python -m app.main "用 Tavily 搜索 LangChain 是什么，并写入 intro.txt"
```

模型可能连续调用两个工具：先 `tavily_search`，再 `write_txt_file`。这正是工具循环存在的原因。

运行测试：

```bash
pytest -q
```

工具相关测试在 `tests/test_tool.py` 和 `tests/test_chain.py` 中。它们使用 Mock 或直接 `tool.invoke()`，不会真正请求 Tavily。

## 十一、自己再加一个工具时怎么做？

最小步骤：

1. 在 `app/tool.py` 用 `@tool` 写函数，写清 docstring 和参数类型。
2. 把这个工具放进 `get_tools()` 返回的列表。
3. 如需新的密钥，在 `Settings` 和 `.env` 中增加字段。
4. 补一个 `tool.invoke(...)` 的单元测试。

例如一个示范加法工具：

```python
@tool
def add_numbers(a: int, b: int) -> int:
    """计算两个整数的和。"""
    return a + b
```

不必改 `main.py`。只要工具出现在 `get_tools()` 里，`bind_tools` 和 `run_tool_loop` 就会自动认识它。

## 十二、本篇小结

本项目的工具调用可以概括为：

```python
tools = get_tools(settings)
llm = model.bind_tools(tools)
answer = run_tool_loop(llm, messages, tools)
```

要记住的核心概念：

- 模型只能**请求**工具，真正执行的是我们的 Python 代码。
- `@tool` 把函数变成带名字、描述和参数说明的预定义工具。
- 官方集成工具（如 `TavilySearch`）也是 `BaseTool`，用法与自定义工具相同。
- `bind_tools` 把工具 schema 发给模型。
- `AIMessage.tool_calls` 表示“请帮我执行这些调用”。
- `ToolMessage` 表示“这次调用的结果”，必须带 `tool_call_id`。
- Tavily 是云端搜索 API，所以需要 `TAVILY_API_KEY`；本地示范工具不需要。
- 给模型的工具列表应当和真正挂载的工具一致。
