# 004：跨会话长期记忆

> 本篇对应当前项目中的 `app/memory.py`、`app/chain.py` 和 `app/main.py`。
>
> 学习目标：分清短期对话历史和长期记忆、理解 `user_id` 与 `session_id` 的分工，以及记忆如何被写入磁盘、注入 Prompt、通过工具增删。

---

## 一、Memory与Context

`002` 里的短期记忆解决的是**同一段对话不要忘了上一句**：

```text
session_id = chat-1
我叫小明。
我叫什么？  → 能回答“小明”
```

它有两个边界：

1. 换一个 `session_id`，历史是空的。
2. 进程退出后，`InMemoryChatMessageHistory` 丢失。

长期记忆要解决的是另一件事：**关于这个人的稳定事实，换会话、重启程序后还在**。

```text
user_id = alice，session_id = chat-1
请记住：我叫小明，喜欢绿茶。

退出程序，再开：
user_id = alice，session_id = chat-2
我喜欢什么茶？  → 仍然能回答“绿茶”
```

两层记忆不要混用：

| | 短期记忆 | 长期记忆 |
|---|---|---|
| 存什么 | 这一轮对话的问答 | 姓名、偏好、身份等稳定事实 |
| 隔离键 | `user_id` + `session_id` | `user_id` |
| 存在哪 | 进程内存 | `data/long_term_memory.json` |
| 进程退出 | 丢失 | 保留 |
| 怎么用 | `MessagesPlaceholder("history")` | 注入系统提示 + 记忆工具 |

## 二、为什么不用把全部聊天记录持久化？

可以把 Redis 历史直接当成“长期记忆”，但那会把闲聊、工具中间态、过期上下文全部留下，Prompt 会越来越长。

本项目采用更常见的拆法：

```text
短期历史 = 当前对话的消息队列
长期记忆 = 少量、可检索、可删除的事实卡片
```

模型需要记住“用户叫小明”时，调用 `save_memory`，而不是指望把整段聊天存盘。

---

## 三、存储格式

`app/memory.py` 中的 `LongTermMemoryStore` 把数据写成 JSON：

```json
{
  "version": 1,
  "users": {
    "alice": [
      {
        "id": "mem_a1b2c3d4",
        "content": "用户叫小明，喜欢绿茶",
        "created_at": "2026-04-08T12:00:00+00:00",
        "updated_at": "2026-04-08T12:00:00+00:00"
      }
    ]
  }
}
```

默认路径来自配置：

```python
memory_path: str = "data/long_term_memory.json"
```

可用环境变量 `MEMORY_PATH` 覆盖。`data/` 已加入 `.gitignore`，避免把个人记忆提交进仓库。

每个用户最多 100 条，单条不超过 500 字。完全重复的内容不会再写一条。

## 四、`user_id` 和 `session_id`

CLI 现在有两个配置项：

```python
config = {
    "configurable": {
        "session_id": args.session_id,
        "user_id": args.user_id,
    }
}
```

含义：

```text
同一个 user_id + 同一个 session_id  → 同一段短期对话
同一个 user_id + 不同 session_id    → 新对话，但共享长期记忆
不同 user_id                        → 记忆完全隔离
```

短期历史的工厂因此改成两个参数：

```python
def get_session_history(session_id: str, user_id: str = "default"):
    key = (user_id, session_id)
    ...
```

`RunnableWithMessageHistory` 通过 `history_factory_config` 把这两个字段传进去。调用时两个 key 都要给，缺一不可。

`user_id` 只允许字母、数字、下划线和短横线，长度 1 到 64。

## 五、记忆如何进入 Prompt？

Prompt 在系统消息末尾留了一个变量：

```python
("system", system_prompt + "\n\n{long_term_memory}")
MessagesPlaceholder(variable_name="history")
("human", "{question}")
```

链在进 Prompt 之前先加载记忆：

```python
RunnablePassthrough.assign(
    long_term_memory=RunnableLambda(load_long_term_memory)
)
```

`load_long_term_memory` 从 `config["configurable"]["user_id"]` 取出用户，再 `store.list(user_id)`。

第一次还没有记忆时，系统提示里大约是：

```text
长期记忆：暂无。若用户提供姓名、偏好……请调用 save_memory。
```

写入之后，下一次任意会话都会看到：

```text
长期记忆（跨会话仍然有效）：
- [mem_a1b2c3d4] 用户叫小明，喜欢绿茶
```

默认最多把最近 15 条直接塞进系统提示。更多时提示模型去调用 `search_memory`。

注意：系统提示每次都会重新生成；长期记忆**不会**变成 `history` 里的 `HumanMessage`。`002` 的消息队列仍然只记本轮问答。

## 六、三个记忆工具

光注入还不够。模型必须能**新增、查找、删除**记忆。`get_memory_tools(store)` 提供：

| 工具 | 作用 |
|---|---|
| `save_memory` | 写入一条陈述句 |
| `search_memory` | 按关键词检索 |
| `forget_memory` | 按记忆 ID 删除 |

这些工具的函数签名里有 `config: RunnableConfig`，LangChain 会注入运行配置，**不会**把 `config` 暴露给模型参数。因此模型只需传 `content` / `query` / `memory_id`，真正的 `user_id` 来自 CLI。

`app/tool.py` 的工具循环必须把 config 传下去，否则记忆会写到默认用户：

```python
selected.invoke(args or {}, config=config)
```

一次“请记住我叫小明”的内部过程：

```text
HumanMessage：请记住我叫小明
AIMessage：调用 save_memory(content="用户叫小明")
ToolMessage：已记住 [mem_a1b2c3d4] 用户叫小明
AIMessage：好的，我记住了
```

和 `003` 一样，工具调用发生在**这一轮内部**。跨轮历史默认仍只保存用户问题和最终回答；但 JSON 文件里已经多了一条长期记忆。下一轮即使 `history` 为空，系统提示里也会出现这条事实。

`save_memory` 和 `write_txt_file` 不要用混：

- 要让助手以后还记得 → `save_memory`
- 要把一段文字导出成文件 → `write_txt_file`

## 七、和工具消息、短期历史的关系

```text
用户问题
   ↓
按 user_id 读取长期记忆，写入系统提示
   ↓
按 user_id + session_id 读取短期 history
   ↓
必要时在本轮内部循环调用工具（包括 save_memory）
   ↓
把本轮 question + 最终答案写入短期 history
   ↓
save_memory 的结果已经落盘，不依赖短期 history
```

因此：

- 换 `session_id`：短期对话清空，长期记忆还在。
- 重启进程：短期对话清空，打开 JSON 后长期记忆还在。
- 换 `user_id`：两层都隔离。

## 九、测试覆盖了什么？

- JSON 文件重启后仍能读到同一条记忆。
- 不同 `user_id` 互相隔离，重复内容不会再写一条。
- 检索和删除。
- 链会把已有记忆注入系统提示；换 session 仍然看得到。
- 模型走 `save_memory` 工具时，写入的是 config 里的 `user_id`。

## 十、以后可以怎么换？

当前实现刻意不引入向量数据库，方便把“跨会话记忆”这条主线看清楚。后续常见升级：

1. 把 JSON 换成 SQLite / Redis / Postgres。
2. 用嵌入向量做语义检索，替代现在的关键词打分。
3. 在每轮结束后自动抽取事实：见 `005_compact与hook.md` 的 MemoryHook，它补上模型没调用 `save_memory` 的漏网之鱼。

对学习阶段来说，先分清这两层就够了：context 是对话，memory 是关于用户的事实。
