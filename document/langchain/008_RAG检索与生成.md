# 008：RAG 向量匹配与生成答案

> 本篇对应当前项目中的 `app/rag/retrieve.py`、`app/tool.py`、`app/chain.py`、`app/main.py` 和 `app/config.py`。
>
> 学习目标：理解检索如何做成工具、如何接到现有 `run_tool_loop`，以及模型怎样根据知识库段落生成带出处的答案。入库见 `007`。

---

## 一、我们要解决什么问题？

`007` 已经把文档变成向量库。本篇解决另一半：用户提问之后，**怎么把问题对上那些块，再让 LLM 按资料说话**。

```text
用户问题
   ↓
把问题变成向量（embedding）
   ↓
在向量库里找最相近的几段
   ↓
作为 ToolMessage 交给模型
   ↓
模型按资料回答，并指出文件名
```

没有 `007` 的索引，这一步只能返回「请先运行 python -m app.ingest」。有索引也不该每轮硬塞全文，那会和 `005` 的 compact 抢窗口。

---

## 二、RAG 不是第四种记忆

四层不要互相替代：

| | 短期历史 | 长期记忆 | 联网搜索 | RAG |
|---|---|---|---|---|
| 存什么 | 本轮对话 | 用户事实卡片 | 不存，现查网页 | 文档切块 |
| 隔离键 | `user_id` + `session_id` | `user_id` | 无 | 共享语料 |
| 存在哪 | 进程内存 | `data/long_term_memory.json` | Tavily | `data/vectorstore/` |
| 怎么取 | 整段插入 Prompt | 注入最近 15 条 + 关键词搜 | 工具 | 向量检索工具 |
| 问什么时用 | “我刚才说了什么” | “我喜欢什么茶” | “今天有什么新闻” | “本项目 compact 压缩的是什么” |

```text
记忆 = 关于这个人
RAG  = 关于这份资料
搜索 = 关于网上现在
```

不要把检索结果伪装成长期记忆，也不要伪装成 `HumanMessage`。

---

## 三、为什么做成工具，而不是每轮硬塞？

### A. Naive RAG：每轮必检索

```text
question → 检索 top-k → 塞进 Prompt 的 {context} → 调模型
```

实现短，闲聊也会检索，无关片段污染上下文。

### B. 工具型 RAG：模型决定要不要查

```text
question → 模型判断
            ├─ 闲聊 / 用户事实 / 网上近况 → 不调 RAG
            └─ 问本地资料               → search_knowledge(query)
```

本项目已经有 `run_tool_loop`（`003`）和「少量注入 + 工具深挖」的记忆（`004`）。检索走同一条路。

第一版选 **B**：

- 失败时只是工具返回「知识库没有相关内容」，不会把整段对话带偏。
- 和 `memory`、`search` 对模型来说长得一样。
- compact 仍然只压短期 history；RAG 片段每轮现查，**不写进** `InMemoryChatMessageHistory`。

`app/chain.py` 不要增加 `{context}` 变量。

## 四、一次带检索的问答长什么样？

问「长期记忆存在哪里？」且 `--rag`、已 ingest：

```text
invoke({question: "长期记忆存在哪里？"}, config={user_id, session_id})
        │
        ▼
读长期记忆，注入 system（004，与 RAG 无关）
拼上 history + 当前问题
        │
        ▼
CompactHook / RetryHook（005）
        │
        ▼
第 1 次模型调用
  → tool_calls: search_knowledge(query="长期记忆 存储路径")
        │
        ▼
retrieve.search_index → 带出处的几段文字
ToolMessage 回填
        │
        ▼
第 2 次模型调用
  → 「存在 data/long_term_memory.json，按 user_id 隔离。见 DOCUMENT/004_长期记忆.md。」
        │
        ▼
StrOutputParser → CLI
本轮写入短期历史的只有：用户问题 + 最终答案
```

和 `003` 没有新协议，只是多了一个工具。

## 五、向量匹配：`retrieve.py`

`store.KnowledgeIndex.search()` 负责「空间里谁近」。`retrieve.py` 负责给模型看的那串字：

1. 空 query → 「检索词不能为空。」
2. 超长 query 截到 2000 字，避免 embedding 被拖垮。
3. 空库 → 「知识库没有相关内容。请先运行 python -m app.ingest。」
4. 有库但没命中 → 「知识库没有相关内容。」
5. 命中则格式化为：

```text
[1] DOCUMENT/004_长期记忆.md
短期历史按 session 隔离，长期记忆按 user_id 持久化到 JSON。
存在 data/long_term_memory.json，换会话、重启后仍有效。

[2] DOCUMENT/002_消息队列.md
短期历史保存在进程内存的 InMemoryChatMessageHistory 中。
```

默认 `top_k=4`（`RAG_TOP_K`）。内存向量库用纯 Python 余弦（见 `007` 的 `store.py`），不依赖 numpy。

`search_index` **不接收 `user_id`**，避免和记忆工具混权限。

## 六、`search_knowledge` 工具：`tool.py`

检索算法在 `app/rag/`，工具层只包装：

```python
@tool
def search_knowledge(query: str) -> str:
    """在本地知识库中检索相关段落。

    当用户询问本项目机制、已入库文档、或明确要求根据资料回答时使用。
    不要用它查询用户自身事实（那是 memory），也不要用来搜网上新闻（那是 search）。
    """
```

`get_tools()` 仅在 `settings.rag_enabled` 为真时挂上它。测试可以注入 `knowledge_index`，不必碰真实 embedding。

约定：

- 回答应指出文件名；资料不够就说不够，不拿检索噪声编造。
- 没有开启 RAG 时，工具列表与 `001`～`006` 完全一致。

## 七、如何接到现有链上

对齐 MCP：可选、可关、不改 `run_tool_loop`。

```text
get_tools(...)                 ← 003 的本地工具 + 004 的 memory
  + search_knowledge           ← 仅 rag_enabled
  + extra_tools                ← 006 的 Blender MCP
        ↓
model.bind_tools(tools)
        ↓
run_tool_loop                  ← 原样复用
```

系统提示仍然是：

```text
system（身份 + 工具名单 + 长期记忆）
+ history
+ 当前问题
```

启用 RAG 时追加分工：问项目机制 / 已入库资料 → `search_knowledge`；用户自身 → `memory`；网上近况 → `search`。不要把整份文档目录写进 system，那是 `007` ingest 的事。

`app/main.py`：

- `--rag` 或 `RAG_ENABLED=true` 打开本进程的检索工具
- 入库仍用 `python -m app.ingest`（`007`）

空库时工具返回明确提示，不要静默胡编，也不要让整个 CLI 起不来。

## 八、和 compact、工具历史的关系

`005` 的 compact 压缩的是短期 `history`。RAG 片段的生命周期是：

```text
本轮内部：search_knowledge → ToolMessage → 模型看见 → 生成答案
跨轮历史：只有用户问题 + 最终答案
向量库：  文档块一直在，直到 007 再次 ingest 覆盖
```

因此：

- 检索结果不要当长期记忆存。
- 工具循环进行中仍然不 compact，避免拆开 `tool_call_id`。
- 下一轮再问相关问题，允许模型再调一次检索。不要指望 history 里还留着原文。

这和 `003` 对 Tavily 结果的处理一致：证据属于这一轮，不是下一轮的记忆。

## 九、配置与运行

本篇用到的配置：

| Python 字段 | 环境变量 | 默认 | 作用 |
|---|---|---|---|
| `rag_enabled` | `RAG_ENABLED` | `false` | 是否挂上 `search_knowledge` |
| `rag_top_k` | `RAG_TOP_K` | `4` | 返回块数 |
| `embedding_model` | `EMBEDDING_MODEL` | 见 `007` | 问题也要 embed 才能匹配 |

先按 `007` 入库，再问：

```bash
python -m app.ingest
python -m app.main --rag "长期记忆存在哪里？和短期历史有什么区别？"
```

合格回答应提到：

- JSON 路径 `data/long_term_memory.json`
- `user_id` vs `session_id`
- 出处 `DOCUMENT/004_长期记忆.md`

对照题，确认模型没有乱用 RAG：

```bash
python -m app.main --rag --user-id alice "我喜欢什么茶？"
# 应走长期记忆

python -m app.main --rag "今天 LangChain 有什么更新？"
# 应走 Tavily（若配置了 Key）
```

## 十、测试覆盖了什么？

`tests/test_rag.py` 里属于本篇的部分：

- 两篇文档入库后，query 命中相关那块。
- 空库、空 query 返回说明文字，不抛异常。
- `top_k` 限制返回条数；超长 query 不报「检索失败」。
- `RAG_ENABLED=false` 时工具列表没有 `search_knowledge`。
- `build_chain` 挂上假索引后，能走完「模型请求工具 → ToolMessage → 最终答案」。

不测真实 Chroma，不测真实 embedding 账单。

## 十一、以后可以怎么换？

第一版刻意不做这些：

1. **轻量注入 + 工具深挖**：每轮先塞 0～3 条摘要，细节再调工具。
2. **混合检索**：向量 + BM25。中文专有名词、文件名往往关键词更稳。
3. **查询改写**：用户说「那个 json 文件」时扩成「长期记忆路径」。
4. **Rerank**：用更小的模型对 top-k 再排一次。
5. **PDF / 代码文件**（属于扩展 `007` 的上传）。
6. **把 `search_memory` 也改成向量**：独立改动。

评估可以做一份很小的 gold 集：十个「问 `DOCUMENT/`」的问题和期望 `source`，看召回对不对。那是检索质量，不是链能不能跑。

## 十二、本篇小结

```text
007 准备好向量库
        ↓
008 retrieve.py 按问题做向量匹配
        ↓
tool.py 把结果变成 search_knowledge
        ↓
chain.py / run_tool_loop 让模型看 ToolMessage 再生成答案
```

记住：

- **先检索再生成**，证据来自本地文档，不是模型参数里的印象。
- 检索做成工具，复用 `run_tool_loop`，不要每轮硬塞 `{context}`。
- compact 不保存检索片段；长期记忆不保存文档。
- 默认关闭；`--rag` 只打开问答侧，入库仍是 `007` 的命令。
