# 002：消息队列与输出方式

> message 数组表示“一次模型调用的完整输入，模型每次调用时，通常接收的是一个消息队列，这整个数组会作为本次调用的上下文发送给模型。
>

---

## 一、这里说的“消息队列”是什么？

在聊天模型中，我们通常不会只发送一个字符串，而是发送一个消息数组：

```python
messages = [
    {"role": "system", "content": "你是一个有帮助的助手。"},
    {"role": "user", "content": "我叫小明。"},
    {"role": "assistant", "content": "你好，小明。"},
    {"role": "user", "content": "我叫什么？"},
]
```

它更准确地说是**有顺序的消息列表**，而不一定是严格意义上的并发队列。消息按照先后顺序组成一次模型输入：

```text
旧消息 → 新消息 → 当前问题
```

在本项目中，历史保存在：

```python
_session_store: dict[str, InMemoryChatMessageHistory] = {}
```

每个 `session_id` 对应一个 `InMemoryChatMessageHistory`，其中的 `messages` 属性就是当前会话的消息数组。

---

## 二、消息的基本角色

LangChain 使用消息对象表达聊天内容。常见类型包括：

```python
from langchain_core.messages import (
    SystemMessage,
    HumanMessage,
    AIMessage,
    ToolMessage,
)
```

### 1. `SystemMessage`：系统消息

系统消息用于定义模型的身份、规则、目标和约束。

```python
SystemMessage(content="你是一个有帮助的中文 AI 助手。")
```

在本项目中，下面这段 Prompt：

```python
("system", SYSTEM_PROMPT)
```

会被转换为一个系统消息。它通常位于消息列表的前面。

系统消息不是普通用户问题。它是给模型的行为指导，但不同模型对系统指令的具体遵循程度可能不同，因此敏感场景仍需要应用层校验。

### 2. `HumanMessage`：人类/用户消息

`HumanMessage` 表示用户输入，也就是对话中需要模型回答的问题。

```python
HumanMessage(content="什么是 LangChain？")
```

本项目中的：

```python
("human", "{question}")
```

在运行时会把 `question` 的值生成一条 `HumanMessage`。

LangChain 的 `human` 角色通常对应底层聊天 API 的 `user` 角色。

### 3. `AIMessage`：AI/助手消息

`AIMessage` 表示模型产生的回复。

```python
AIMessage(content="LangChain 是用于构建大语言模型应用的框架。")
```

当一次调用成功后，`RunnableWithMessageHistory` 会把当前用户问题和模型回复写入历史。因此下一次请求可以看到上一轮的 `HumanMessage` 与 `AIMessage`。

`AIMessage` 除了 `content`，还可能包含：

- `tool_calls`：模型请求调用工具的信息。
- `response_metadata`：模型、token、结束原因等元数据。
- `usage_metadata`：输入和输出 token 使用量。
- `additional_kwargs`：底层服务返回的额外字段。

### 4. `ToolMessage`：工具结果消息

`ToolMessage` 表示工具执行后的结果，通常用于工具调用流程：

```python
ToolMessage(
    content="北京今天晴，气温 25°C",
    tool_call_id="call_123",
)
```

典型流程是：

```text
HumanMessage：北京今天天气怎么样？
AIMessage：我要调用天气工具
ToolMessage：天气工具返回晴，25°C
AIMessage：北京今天晴，气温 25°C
```

`tool_call_id` 用于把工具结果和对应的工具调用关联起来。工具调用不是简单地把工具结果伪装成用户消息，否则模型可能无法正确理解消息来源。

---

## 三、角色名称的对应关系

LangChain 的消息类型和常见 API 角色大致对应如下：

| LangChain 消息类型 | Prompt 简写 | 常见 API role | 含义 |
|---|---|---|---|
| `SystemMessage` | `system` | `system` | 系统规则和身份 |
| `HumanMessage` | `human` | `user` | 用户输入 |
| `AIMessage` | `ai` | `assistant` | 模型回复 |
| `ToolMessage` | `tool` | `tool` | 工具执行结果 |

`human` 和 `user`、`ai` 和 `assistant` 是不同抽象层的叫法：LangChain 在内部使用自己的消息类；发送到具体模型供应商时，再由对应的模型集成转换为供应商需要的格式。

## 四、本项目的 Prompt 如何形成消息数组？

`app/chain.py` 中的 Prompt 是：

```python
prompt = ChatPromptTemplate.from_messages(
    [
        ("system", system_prompt),
        MessagesPlaceholder(variable_name="history"),
        ("human", "{question}"),
    ]
)
```

这里的 `MessagesPlaceholder("history")` 是一个占位符。它不会自己创建固定内容，而是等待运行时传入历史消息。

第一次调用：

```python
chain.invoke(
    {"question": "我叫小明"},
    config={"configurable": {"session_id": "default"}},
)
```

当历史为空时，Prompt 展开后大致是：

```python
[
    SystemMessage(content="你是一个有帮助的中文 AI 助手……"),
    HumanMessage(content="我叫小明"),
]
```

第二次调用：

```python
chain.invoke(
    {"question": "我叫什么？"},
    config={"configurable": {"session_id": "default"}},
)
```

Prompt 展开后大致是：

```python
[
    SystemMessage(content="你是一个有帮助的中文 AI 助手……"),
    HumanMessage(content="我叫小明"),
    AIMessage(content="你好，小明。"),
    HumanMessage(content="我叫什么？"),
]
```

也就是说，系统消息由 Prompt 固定生成；历史消息由 `history` 占位符插入；当前问题由 `{question}` 生成。

注:

消息队列还能写成:

```
messages = [
    {"role": "system", "content": "你是一个有帮助的中文 AI 助手……"},
    {"role": "user", "content": "我叫小明"},
    {"role": "assistant", "content": "你好，小明。"},
    {"role": "user", "content": "我叫什么？"},
]
```

这种形式，不使用SystemMessage, HumanMessage, AIMessage类，而是写成:

```
messages.append({"role": "", "content": ""})
```

显示传入role角色，但是不推荐这种写法，因为字典格式只适合**基础对话**；做**工具调用**强烈推荐用对象写法，因为 AIMessage 需要携带`tool_calls`字段，字典写起来很麻烦。



## 五、`RunnableWithMessageHistory` 如何管理队列？

​	消息队列是表示某一次模型调用时发送的完整上下文，如果要多次连续调用模型，就需要将上一次的消息连带着本次的问题作为上下文一次发给模型。例如deepseek官方文档中是这样实现的:

![image-20260915005833294](https://cdn.jsdelivr.net/gh/APpery1/pic@main/img/image-20260915005833294.png)

在**第一轮**请求时，传递给 API 的 `messages` 为：

```json
[
    {"role": "user", "content": "What's the highest mountain in the world?"}
]
```

在**第二轮**请求时：

1. 要将第一轮中模型的输出添加到 `messages` 末尾
2. 将新的提问添加到 `messages` 末尾

最终传递给 API 的 `messages` 为：

```json
[
    {"role": "user", "content": "What's the highest mountain in the world?"},
    {"role": "assistant", "content": "The highest mountain in the world is Mount Everest."},
    {"role": "user", "content": "What is the second?"}
]
```

---------------------------------------------------------------------------------------------------------------------------------------------



本项目返回的是：

```python
return RunnableWithMessageHistory(
    base_chain,
    get_session_history,
    input_messages_key="question",
    history_messages_key="history",
)
```

它可以分成“读历史”和“写历史”两个阶段理解。

### 阶段 1：根据 `session_id` 取出历史

调用时必须提供：

```python
config = {
    "configurable": {
        "session_id": "default"
    }
}
```

LangChain 使用这个 `session_id` 调用：

```python
def get_session_history(session_id: str):
    if session_id not in _session_store:
        _session_store[session_id] = InMemoryChatMessageHistory()
    return _session_store[session_id]
```

不同的 `session_id` 对应不同的消息列表，因此会话之间互相隔离。

### 阶段 2：把历史注入 Prompt

`history_messages_key="history"` 告诉 `RunnableWithMessageHistory`：

```text
把取出的历史消息放到输入字典的 history 字段
```

于是 Prompt 中的：

```python
MessagesPlaceholder(variable_name="history")
```

就能接收到这些消息。

### 阶段 3：加入当前用户消息

`input_messages_key="question"` 告诉它：

```text
当前用户输入位于 question 字段
```

因此：

```python
{"question": "我叫什么？"}
```

最终会生成当前这一轮的 `HumanMessage`。

### 阶段 4：调用模型

`base_chain` 执行：

```python
prompt | model | output_parser
```

模型接收完整消息数组，生成 `AIMessage`。输出解析器再把它转换为字符串或 JSON。

### 阶段 5：把本轮输入和输出写回历史

调用成功后，消息历史会增加两条消息：

```text
HumanMessage：当前问题
AIMessage：模型回答
```

因此连续调用两次后，通常有四条历史消息：

```python
[
    HumanMessage(...),
    AIMessage(...),
    HumanMessage(...),
    AIMessage(...),
]
```

本项目的测试也验证了：

```python
assert len(get_session_history(session_id).messages) == 4
```

需要区分：`StrOutputParser` 或 `JsonOutputParser` 改变的是返回给调用者的结果形式，不会把历史中的 AI 回复变成用户消息。历史仍然按照用户消息和 AI 消息的角色保存。

## 六、阻塞式输出：`invoke()`

当前项目使用的是阻塞式调用：

```python
answer = chain.invoke(
    {"question": question},
    config=config,
)
print(answer)
```

它的特点是：

1. 发出完整请求。
2. 等待模型生成结束。
3. 等待输出解析完成。
4. 返回完整结果。
5. CLI 一次性打印答案。

示意：

```text
用户输入
   ↓
等待网络请求
   ↓
等待模型完整生成
   ↓
等待解析器完成
   ↓
一次性得到完整答案
```

优点：

- 代码简单。
- 适合测试、批处理和需要完整结果的业务。
- JSON 解析等后处理比较自然。

缺点：

- 模型生成期间用户看不到内容。
- 长答案会有明显等待感。

---

## 七、流式输出：`stream()`

流式调用会在模型生成过程中不断返回片段：

```python
for chunk in chain.stream(
    {"question": question},
    config=config,
):
    print(chunk, end="", flush=True)
print()
```

示意：

```text
用户输入
   ↓
收到“LangChain”
   ↓
收到“是一个”
   ↓
收到“大语言模型应用框架”
   ↓
生成结束
```

`flush=True` 很重要，它会让终端尽快显示每个片段，而不是等到标准输出缓冲区积累后再显示。

### 阻塞式与流式对比

| 方式 | 方法 | 返回时机 | 适合场景 |
|---|---|---|---|
| 阻塞式 | `invoke()` | 完整结果生成后 | 测试、批处理、结构化数据 |
| 流式 | `stream()` | 生成过程中不断返回 | CLI 聊天、网页打字机效果 |
| 异步阻塞 | `ainvoke()` | 异步等待完整结果 | 异步 Web 服务 |
| 异步流式 | `astream()` | 异步逐段返回 | 高并发流式应用 |

---

## 八、流式输出与 JSON 解析的关系

这是一个重要区别。

### `StrOutputParser` 的流式输出

普通字符串解析器可以比较自然地逐片段输出：

```python
for chunk in chain.stream({"question": question}, config=config):
    print(chunk, end="", flush=True)
```

### `JsonOutputParser` 的流式输出

JSON 需要完整或部分解析。例如模型可能依次产生：

```text
{
{"answer":
"你好"
}
```

在生成前半段时，内容还不是完整 JSON。`JsonOutputParser` 在流式场景下可能返回部分字典，也可能直到结构足够完整后才能得到有意义的结果。

因此学习阶段建议：

- 想观察文字生成过程：使用 `StrOutputParser + stream()`。
- 想得到最终可靠 JSON：使用 `JsonOutputParser + invoke()`。
- 需要 JSON 流式传输时，要额外设计增量 JSON、事件协议或前端拼接逻辑。

## 九、流式消息是如何进入历史的？

流式输出只是改变“结果交付给调用者的方式”，并不意味着每个 token 都立即作为一条 `AIMessage` 写入历史。

通常可以这样理解：

```text
HumanMessage：在调用开始时确定
AIMessage：模型生成期间逐步产生内容
历史记录：在本轮调用完成时保存完整的 AI 回复
```

最终历史仍然应当是一条完整的 `AIMessage`，而不是很多条碎片消息：

```python
[
    HumanMessage(content="你好"),
    AIMessage(content="你好！有什么可以帮助你的吗？"),
]
```

这也是为什么历史消息适合表示“对话轮次”，而不是表示每一个 token。

对于复杂的流式、工具调用或自定义存储场景，需要特别检查所使用的 LangChain 版本和 Runnable 的历史实现。不要假设所有流式事件都会自动持久化。

## 十、如何直接观察消息数组

可以在 Prompt 和模型之间插入一个调试 Runnable：

```python
from langchain_core.runnables import RunnableLambda


def inspect_messages(prompt_value):
    messages = prompt_value.to_messages()
    for index, message in enumerate(messages):
        print(index, type(message).__name__, message.content)
    return prompt_value

base_chain = prompt | RunnableLambda(inspect_messages) | model | output_parser
```

可能看到：

```text
0 SystemMessage 你是一个有帮助的中文 AI 助手……
1 HumanMessage 我叫小明
2 AIMessage 你好，小明
3 HumanMessage 我叫什么？
```

这个调试步骤非常适合理解：

- `system_prompt` 到底放在哪里。
- `history` 是否正确注入。
- 当前 `question` 是否生成了 `HumanMessage`。
- 消息的顺序是否符合预期。

## 十一、本篇小结

本项目的一次带历史调用可以概括为：

```text
session_id
   ↓
取出 InMemoryChatMessageHistory.messages
   ↓
插入 Prompt 的 history 占位符
   ↓
加入当前 HumanMessage
   ↓
调用 ChatOpenAI
   ↓
得到 AIMessage
   ↓
输出解析
   ↓
把本轮 HumanMessage 和 AIMessage 写回历史
```

要记住四类核心消息：

- `SystemMessage`：系统规则。
- `HumanMessage`：用户输入。
- `AIMessage`：模型回复。
- `ToolMessage`：工具执行结果。

要记住两种调用方式：

- `invoke()`：等待完整结果后返回。
- `stream()`：模型生成时逐段返回。

消息数组保存的是有顺序、有角色的对话消息；流式输出的片段不等于历史中的独立消息。理解这几层关系，是继续学习 Agent、工具调用、RAG 和 LangGraph 持久化的基础。
